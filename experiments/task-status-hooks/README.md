# 任务状态 Hooks 接入原型

这是隔离的可行性验证，不是已上线的任务状态实现。不会被 Swift Package 编译或 DMG 打包；脚本不会自动修改当前 HUD、用户配置、Hook 信任记录，也不会启动模型任务。原型使用 Node.js 内置模块；这不意味着正式应用将新增 Node.js 依赖。

## 当前结论（2026-09-16）

- 本机桌面应用内置运行时为 `codex-cli 0.154.0-alpha.6.2`，`hooks` 特性已启用。
- 使用该可执行文件启动独立实例，临时传入四个 Hook 定义后，`hooks/list` 均能识别：`UserPromptSubmit`、`Stop`、`Interrupt`、`SessionEnd`；错误数为 0，信任状态均为 `untrusted`。没有持久化这些定义，也没有执行或信任 Hook。
- 本地协议与接收器的 29 项测试通过；现有任务状态的 34 项检查此前已通过，生产代码本轮未改动。
- 用户完成信任后，四类定义的信任状态均变为 `trusted`。用户随后在桌面 App 的当前项目目录新建只读任务「查看 Package.swift 项目信息」；接收器于本地时间 20:08:53 收到该任务的 `Stop` 回调，会话及轮次 ID 与宿主返回的已完成任务一致。真实桌面回调链路已打通；后续双任务及已结束任务缓存恢复验证见下文，执行中的任务恢复仍有覆盖限制。
- 初版快照仅保留最后状态，虽有 3 次状态更新，不能追溯每次对应的事件，因此不能据此声称已验证 `UserPromptSubmit`。现已补充最多 128 条状态更新事件的元数据记录，用于下一轮验收；不补造既往事件。
- 用户已明确同意项目级试验：已单独创建当前项目的 `.codex/hooks.json` 并启动接收器。未由代理修改全局配置或信任记录。本机专用配置通过 `.git/info/exclude` 排除，不随仓库提交。
- **Hooks 单独不足以承诺准确运行数量。** 提交提示后，其他 Hook 可能阻止执行；收到 `Stop` 后也可能续跑；任务中途接入、宿主崩溃及上报丢失都需要额外校准来源。

因此，本原型明确输出 `submittedCandidates`（提交后可能仍在执行的会话数），而将 `authoritativeRunningCount` 保持为 `null`。禁止把候选数直接接入正式 UI 的“运行中”数字。

### 双任务真实桌面验证

2026-09-16，用户在同一项目原目录启动两个名称均为「查看 Package.swift 项目语言」的本地任务，要求等待 45 秒后只读检查项目。按不同会话 ID 区分任务 A/B，接收记录如下（Asia/Shanghai）：

| 接收时间 | 任务 | 事件 |
| --- | --- | --- |
| 20:11:45.850 | A | `UserPromptSubmit` |
| 20:11:48.929 | B | `UserPromptSubmit` |
| 20:12:39.071 | A | `Stop` |
| 20:12:45.642 | B | `Stop` |

20:11:58 的原型快照显示候选会话数为 2；紧接着通过宿主只读任务接口核对，两项均为 `active` / `inProgress`，会话、轮次和目录匹配。随后通过宿主等待接口确认两项均正常完成；20:12:46 的原型快照显示候选会话数为 0、停止观测数为 2。两个任务各收到配对的提交/停止事件，本轮未观察到漏计或重复计数。

限制：这是两项新建本地任务的样本，不覆盖旧会话热加载、远程任务、子代理、中断或异常退出。中间计数为 1 的阶段没有单独采样，不将事件顺序推导冒充独立实时观测。当时接收器重启前的首轮任务缓存仍显示 1 项未知；该遗留项已按下节修复，但不能把本轮候选数归零等同于全局已确认空闲。宿主任务工具仅用作人工验收对照，不是可供独立 HUD 直接调用的已实现接口。

### 旧缓存未知状态修复

原实现重启时将所有记录无差别降为未知，且 `SessionEnd` 会覆盖已有终态。现在保留精确到轮次的已确认完成/中断事实；未结束记录降为未知，已有 `Stop` 仍保留为停止观测，不冒充成功完成。

启动时仅对缓存里尚不确定的轮次做一次只读校准：按会话 ID 查询本地 SQLite 定位对应日志，仅接受匹配轮次的 `task_complete` 或 `turn_aborted`。单次最多检查 32 份日志，每份尾部最多 256 KiB（总计不超过 8 MiB），SQLite 调用超时 1 秒。缺失、损坏、越界路径、尾部截断、未匹配轮次或超过预算的记录保持未确定，不以超时判空闲，也不把启动日志当作持续运行证据。

本机验证：真实缓存的三个测试轮次均找到完成记录，一次校准约 32.6 ms；首轮重启后 `unknown=0`、`confirmedCompleted=3`，再次重启仍为相同结果且读取日志数为 0。原始缓存保留在忽略目录的 `snapshot.before-recovery.json` 中。29 项测试覆盖精确轮次匹配、中断/完成事实保持、旧事件、新轮次、反复重启、日志缺失、路径逃逸与 I/O 上限。真实桌面中断、任务执行中重启及宿主异常退出尚未完成实测。

## 结构与边界

`Hook → 有时限的本地发送器 → Unix socket 接收器 → 元数据快照`

- `bridge.mjs`：事件白名单、接收器、状态归并，以及打印待审阅 Hook 配置的命令。
- `recovery.mjs`：启动时按缓存会话定位日志，使用精确轮次的终态记录修复旧缓存。
- `probe-runtime.mjs`：只在独立运行时实例上验证配置发现能力；不创建/恢复任务，不发起模型请求，不写入信任设置。
- `tests.mjs`：状态归并和真实本地 socket 的合成事件测试。

不设置轮询定时器，不持续扫描会话日志；启动恢复仅检查缓存任务的有界日志尾部。快照只记录会话 ID、轮次 ID、事件对应的观测状态、本地接收时间和恢复计数，并保留最多 128 条已更新状态的事件元数据；不保存提示词、助手回复、工作目录、工具参数或 transcript 路径。恢复不会伪造新的 Hook 事件；重复且被去重的提交不会产生新的状态更新记录，事件记录不是无损全量审计日志。

事件归并原则：

| 事件/情况 | 原型行为 |
| --- | --- |
| `UserPromptSubmit` | 增加候选会话，同一会话不因重复事件或多轮次重复计数 |
| `Stop` | 记为“观察到停止”，不等同成功完成 |
| `Interrupt` | 记录该轮次中断，旧轮次事件不取消新轮次 |
| `SessionEnd` | 未结束任务标未知，保留终态及停止观测，不推定任务成功完成 |
| 长时间无事件 | 不靠超时制造完成或空闲结论 |
| 接收器重启 | 保留终态，未结束任务降为未知，按精确轮次做一次有界终态校准；覆盖范围仍不完整 |
| 超过 512 条记录 | 淘汰旧记录并提示容量缺口；不能当作完整总数 |

不监听 `SubagentStart` / `SubagentStop`，但主任务/子代理的实际事件身份和覆盖范围仍须真实宿主联调验证。Hook 没有可靠的全局事件序列号，原型仅处理部分重复和乱序，不宣称能够完全恢复事件顺序。

接收目录要求当前用户拥有且权限为 `0700`，socket 和快照为 `0600`。拒绝复用已有 socket，避免删除另一个接收器的入口。IPC 不是对同用户恶意进程的认证边界，不应把输入视为可用于安全决策的可信信息。

发送器对输入设置 1 MiB 上限，连接/确认等待上限为 200 ms，脚本内整体处理期限为 500 ms；生成的 Hook 配置超时为 1 秒。超限、格式错误、接收器不存在或无响应时均返回中性的 `{}` 和退出码 0，不阻止任务，不添加提示词，不修改授权结果。时限不包括操作系统启动进程前的调度延迟。

上报失败时采取放行任务的策略，因此事件可能丢失。接收器无法单靠沉默发现宿主崩溃或所有上报丢失；这也是不能报告权威数量的原因。正式接入需要宿主运行状态/快照校准，而不只是延长过期时间。

## 复现本地检查

在仓库根目录执行，需要 Node.js 22 或兼容版本：

```bash
node --test experiments/task-status-hooks/tests.mjs
node experiments/task-status-hooks/probe-runtime.mjs
bash scripts/test-task-status.sh
```

用户已允许并写入项目配置后，用下列只读命令核对真实配置的发现及信任状态：

```bash
node experiments/task-status-hooks/probe-runtime.mjs --project
```

可传入其他安装位置的 Codex 可执行文件：

```bash
node experiments/task-status-hooks/probe-runtime.mjs /absolute/path/to/codex
```

接收器需单独运行在私有临时目录中：

```bash
probe_dir=$(mktemp -d /tmp/hud-hook-probe.XXXXXX)
node experiments/task-status-hooks/bridge.mjs receive "$probe_dir/events.sock"
```

接收器会打印 socket 和快照路径。另一个终端可以用实际 socket 路径生成供审阅的配置，下面命令只打印、不安装：

```bash
node experiments/task-status-hooks/bridge.mjs config /tmp/hud-hook-probe.EXAMPLE/events.sock
```

生成配置包含当前 Node 和脚本的绝对路径，只适用于本机试验。不要将个人路径作为公共默认配置提交；不要直接覆盖已有 `hooks.json`。启用前应合并并检查已有定义，在宿主提供的 Hook 界面审阅并信任。不得使用跳过信任检查的参数。

## 本轮性能样本

这些是独立 Node 原型数据，**不是正式 HUD 的性能改善结果**：

- 接收器空闲 10 秒，`ps` 累计 CPU 时间从 `0:00.03` 到 `0:00.03`，在本次读数精度下没有增量；不能推断为绝对零 CPU 或长期耗电表现。
- 顺序启动 20 次发送器、投递合成事件并收到确认，进程全程耗时中位数 32.6 ms、P95 35.1 ms。
- 异常输入/接收器不存在的三次测试耗时约 41–44 ms；接收器不返回确认的测试约 336 ms，均正常退出且不写模型上下文。

样本短、存在启动和运行时开销。正式设计如通过语义验收，应使用随应用分发的原生 helper，并重新测试空闲、多任务、异常恢复和长时运行。

## 尚未通过的真实宿主验收

当前项目的试验配置已经得到用户许可并写入，用户已完成信任，新建桌面任务的停止回调已验证。现有长会话未观察到回调，不能据此断定原因或假设配置会在活动任务中热加载。全局配置和正式 HUD 保持不变。接收器是临时进程，不安装登录项；退出后再次验证前需显式启动接收器。

1. 两个用户可见主任务并行：本轮两项新建本地任务的提交、同时运行和停止已验证；子代理身份及其他任务来源尚未验证。
2. 超过 30 分钟无工具输出：确认不会仅凭沉默丢失运行态。
3. 正常停止、其他 Hook 阻止提示/要求续跑、中断：确认事件含义及先后顺序。
4. HUD/接收器中途启动或重启：已结束任务的旧缓存修复及反复重启已验证；执行中任务仍需新的有效证据，不将缓存冒充实时运行状态。
5. 宿主异常退出、休眠唤醒、上报超时：确认有独立的缺口检测与恢复手段。

任何一项关键覆盖不足，都应维持候选/未知语义，继续保留现有正式实现，而不是宣称精确模式已经完成。
