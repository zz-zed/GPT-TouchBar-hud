# 任务状态不显示：远程采集

适用于 GPT TouchBar HUD v0.1.40 的普通日志任务监测。把 `scripts/diagnose-task-status.command` 单独发送给故障电脑即可，不需要整个仓库、Python、Xcode、管理员权限或联网。

[下载脚本](https://raw.githubusercontent.com/zz-zed/GPT-TouchBar-hud/refs/heads/main/scripts/diagnose-task-status.command) · [查看源码](https://github.com/zz-zed/GPT-TouchBar-hud/blob/main/scripts/diagnose-task-status.command)

也可在故障电脑的终端粘贴以下命令，下载到桌面后采集 2 分钟：

```bash
curl -fL --connect-timeout 15 --max-time 60 \
  'https://raw.githubusercontent.com/zz-zed/GPT-TouchBar-hud/refs/heads/main/scripts/diagnose-task-status.command' \
  -o "$HOME/Desktop/diagnose-task-status.command" && \
bash "$HOME/Desktop/diagnose-task-status.command" 120 fault
```

下载需要联网，采集过程不访问网络。命令会替换桌面上同名的诊断脚本；桌面的其他文件不受影响。下载失败时不会执行。开始采集后，再发起一轮新的本地 Codex 任务；结束后发送桌面的诊断报告即可。

## 对方如何操作

1. 保持 Codex 和 GPT TouchBar HUD 运行。记录当时额度是否正常、任务区域是否有数字，并确认「设置 → 通用 → 显示任务状态（实验性）」的勾选状态。
2. 打开终端，输入 `bash `（末尾留一个空格），把脚本拖入终端，按回车。
3. 看到「正在监控」后，在 Codex 新开一轮**本地**任务。任务可持续几十秒，例如请 Codex 只读检查一个已有项目。监控期间不要重启 HUD、切换任务开关或改动 Hooks 配置。
4. 默认约 2 分钟后结束。把桌面的 `TouchBar-task-diagnostics-日期-时间-编号.txt` 发回，并注明：新任务大约何时开始/结束，额度是否正常，任务数字是否出现。必要时可按 Control-C 提前停止，已采集部分会保留。

延长到 3 分钟：`bash 脚本路径 180`。脚本支持 2–600 秒，正常采集建议至少 120 秒。请发送采集报告，不需要发送原始会话日志、数据库或账号文件。

## 升级后新任务也不显示时

“Codex 保持运行 → HUD 升级至 v0.1.40 → 新发起的任务也不显示 → 完全退出并重开 Codex 后恢复”需要按持续故障调查。仅凭启动基线漏计，不能完整解释这条现象；也不能据恢复结果直接认定 Intel 兼容性或 Codex 本身故障。

如果再次出现，建议分阶段采集。每次都先开始采集，再发起新任务，并记下 Touch Bar、HUD 浮窗/菜单中的任务提示是否出现：

1. 保留故障现场，运行 `bash 脚本路径 120 fault`。先完成这份报告再重启任何应用。
2. 保持 Codex 运行，仅退出并重新打开 HUD，运行 `bash 脚本路径 120 after-hud-restart`。如果恢复，保留这两份报告即可。
3. 若仍异常，再完全退出并重开 Codex，运行 `bash 脚本路径 120 after-codex-restart`，与前两份比较。

阶段标记只写入报告，脚本不会自行重启任何应用。报告记录 HUD/Codex 进程的变化，便于确认实际重启了谁。HUD 重启后恢复，会将范围收窄到 HUD 的运行状态；仅重启 Codex 后恢复，则仍需区分宿主数据恢复与其带动的 HUD 重建。任何一次恢复都不单独证明具体根因。

若在未来一次原计划的升级中采集，可在升级前运行 `bash 脚本路径 600 before-upgrade`，覆盖旧版到新版的过程，并记录升级完成和新任务开始的时刻。

## 采集范围

- 系统版本、进程架构、正在运行的 HUD / Codex 的 PID、启动时间、进程变化，以及对应应用目录的版本、Build 和是否位于 Applications。版本信息每次从 Info.plist 重新读取，避免 NSBundle 缓存跨升级沿用旧值；它不是对进程内存中版本常量的读取。
- HUD 已保存的任务显示、Hooks 和 Touch Bar 常驻开关；这些是保存值，不直接证明运行中 HUD 内存里的值。
- 默认 `.codex`、终端 `CODEX_HOME` 与 `launchctl getenv CODEX_HOME` 指向的候选目录。报告仅使用 H1 等匿名别名，不导出真实路径。GUI 进程实际继承的环境没有被读取；候选目录不能直接当成 HUD 的实际目录。
- 只读查询 `state_5.sqlite`。检查必要字段，统计未归档会话的固定来源类别，使用 v0.1.40 原有查询选择最多 32 个主会话。另外导出最多 32 个最近未归档会话的匿名索引元数据，标明是否被 HUD 选中、路径是否符合约束，帮助识别新会话被筛选排除的问题。索引年龄按生产查询使用的 `updated_at` 秒值计算；不读取标题、提示词或账号信息，也不读取被排除会话的日志。
- 每文件每次最多读 256 KiB，建立基线后增量读取。记录开始、完成、中断、工具完成和 Token 事件的数量，以及无效轮次 ID、时间戳、JSON、读取失败、跳读、截断等情况。文件用 H1-T1 等别名，轮次 ID 不导出。
- 按普通模式生命周期规则做独立推算：监控前开始的历史任务保持未知，明确开始才可激活，迟到工具事件不能复活已完成任务。报告不包含对话、工具输出、完整日志、原始错误、账号、Token 数值或真实文件路径。

脚本不修改 HUD 偏好、Hooks、Codex 配置、数据库或日志，不调用额度接口、安装程序或启动/退出 HUD。只创建桌面报告和运行期间的私有临时文件；临时文件在退出时清理。SQLite 子进程遇到 5 秒超时仅终止该诊断子进程。数据库忙、输出超限或解析失败都会显式记录，不把失败当成确认无任务。

## 如何据报告分析

| 报告证据 | 下一步 |
| --- | --- |
| 已保存的任务开关关闭 | 先核对现场开关与运行实例；不能归因 Intel |
| HUD 不在运行、存在多实例、版本不是 0.1.40 / Build 43 | 核对实际运行应用与启动路径 |
| 数据库不存在、必要字段不兼容、读取失败 | 检查数据目录、权限或宿主数据格式 |
| 有来源类别，但主会话筛选没有候选 | 核查新任务是否本地任务，以及宿主来源标记是否变化 |
| 最近索引中的新会话没有被 HUD 选中 | 结合开始时刻、固定来源类别和索引更新顺序，检查来源筛选或 32 个候选的范围 |
| 新任务期间没有开始事件，只有工具或 Token 事件 | 排查日志是否及时落盘、开始事件是否遗漏或超出读取范围 |
| 新任务出现开始事件，但 ID / 时间戳无效 | 检查宿主日志格式与解析兼容性 |
| 独立模型在新任务后显示 running，现场 Touch Bar 仍为空 | 上游证据可识别；继续核查 HUD 实际目录、保存开关与内存状态、回调及渲染链路 |
| 开始早于 HUD 启动，只有初始基线、没有新的明确开始 | 符合既有启动恢复漏计机制；再结合一轮新任务的结果区分 |

`independentModelRunning` 是脚本观察的普通日志推算，不是 HUD 内存、真实任务总量或 Touch Bar 渲染结果。脚本比 HUD 晚启动，基线阶段的零也不证明 HUD 没识别任务。Hooks 模式仅记录开关，不安装、调用或模拟 Hooks；若开关启用，普通模型只能帮助检查日志，仍需另查真实接入与投递。

报告是逐行 JSON，保留采集时间线和最终 footer。`completed:false` 或缺少 footer 表示未完整结束，已有样本仍可用于分析。SQLite 使用 macOS 自带的 `-readonly -json` 能力；若系统工具不支持，将记录失败而不会要求安装替代工具。

## 本地验证

运行 `python3 Tests/TaskDiagnosticProbeTests.py`，隔离验证历史基线、新任务增量读取、终态后的迟到事件、有界尾读、截断、无效事件、路径约束、隐私输出，以及数据库不存在、结构不兼容与成功空结果的区别。另验证采集阶段、匿名索引与来源排除，以及模拟进程变化的记录；模拟没有重启本机应用。Python 仅用于开发测试，分发脚本不依赖 Python。

另以本机真实应用与数据执行短时只读采集。该验证不代表故障 Intel / macOS 15.8.1 / 宿主 26.1002.51308 已完成实机验收。
