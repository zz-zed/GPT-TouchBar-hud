## 目标与连续记录的含义

覆盖 Codex 持续运行、用户确认升级后 HUD 安装并重启的场景。一次导出能够关联旧版的故障前记录、安装过程、新版启动及连接和任务监测恢复；安装失败或回退时仍能取得已有证据。

“连续”指诊断文件跨版本保留、不同进程记录可关联、采集空窗可解释。HUD 退出期间不能实时观察其业务状态；安装助手只记录升级行为，不承担 Codex 任务监测。新版恢复后读取的宿主历史事件必须标为恢复后观察，不能填补成停机期间实时采集。磁盘写入失败、强制退出和突然断电仍可能丢失尾部记录，不能承诺零丢失。

## 现有基础与必要补充

| 当前机制 | 追加设计 |
| --- | --- |
| 诊断目录独立于 App bundle | 保持固定位置，升级和回退不清空日志、不重置用户记录开关 |
| `AppUpdateProgressChannel.Context.sessionID` 标识一次更新 | 复用为 `updateSessionID`，仅关联本次升级，不作为设备标识 |
| 旧 HUD 启动独立安装脚本，进度助手可独立存活 | 旧 HUD、安装脚本和新版各记录自己亲历的事件；进度助手仅补充自身故障或状态观察 |
| `install.json` 原子覆盖当前安装阶段 | 保持原状态通道，另增有界追加事件，不能事后用最后状态伪造完整过程 |
| 新版用启动参数和受校验的更新目录写 `launch.json` | 保留既有安装完成判断，另外记录诊断接续和分模块业务恢复 |
| 现有普通诊断记录器有进程会话和退出标记 | 助手使用独立轻量写入接口，不调用普通记录器的启动或退出标记逻辑 |

对升级诊断的任何写入失败均不改变原有替换、回退、退出或启动确认判断。未经验证的目录参数、进度快照或 PID 单独存在均不能建立可信关联。

## 升级会话与事件协议

公共字段沿用 M1 类型化白名单，补充可选 `updateSessionID`、`writerRole`、`eventID`、本进程真实版本与 Build。角色固定为 `oldHUD`、`installer`、`progressHelper`、`newHUD`、`restoredHUD`。进程会话随机 ID 每次启动独立生成，事件 ID 使用会话 ID 加序号去重。

版本与 Build 在各进程启动时从自己的构建元数据捕获；目标版本来自已经校验的安装包元数据。不在替换后重新读取安装路径的 Info.plist 来代表仍运行的旧进程版本。缺失 Build 标为未知。

旧版将来源与目标版本、来源会话、协议版本、当时记录开关及清除代次写入经过路径与所有者校验的最小交接状态。沿用现有私有通道，不导出其中的 `targetPath`、目录参数或自由文本。诊断目录根据固定应用身份解析，不信任任意传入输出路径。

| 阶段 | 事件及生产者 | 记录含义 |
| --- | --- | --- |
| 准备交接 | 旧 HUD：`update.handoffPrepared` | 安装包已准备，目标版本已知，即将交接；不等于安装完成 |
| 退出 | 旧 HUD：`app.exitRequested`，原因 `update`；尽力记录刷新结果 | 与手动退出、宿主退出、异常结束区别；刷新未确认不写成功 |
| 等待结束 | 安装脚本：`update.oldProcessExitObserved` 或 `update.oldProcessExitTimedOut` | 根据原安装器等待结果记录，不延长既有等待窗口 |
| 安装 | 安装脚本：备份、替换各阶段的开始及结果 | 写入点位于实际操作前后，不以 UI 轮询推断执行成功 |
| 启动 | 安装脚本：`update.launchRequested`、原启动回执检查结果或超时 | 原启动成功仅表示现有回执条件通过，不等于所有业务恢复 |
| 新进程接续 | 新版：`app.started`、`update.continuationAccepted` 或拒绝原因 | 新版本、新会话、有效升级关联；无合法交接时正常独立启动 |
| 恢复 | 新版：连接、任务监测、显示各自的恢复观察 | 分别报告成功、失败、未启用、未知或尚未观察；不制造单一“全部正常” |
| 回退 | 安装脚本：回退开始、恢复旧包、恢复启动及失败；恢复版：接续事件 | 清楚区分实际运行版本和原目标版本 |
| 中断 | 可存活的助手：安装进程中断观察；下一次 HUD 启动：未完成交接观察 | 明确观察来源和时间，不推断失去证据后的具体失败阶段 |

新版运行与旧 HUD 停机区间，在摘要标明“HUD 业务采集空窗”。有旧进程退出观察及新进程启动时间时给出区间；只有单侧边界或系统时钟跳变时，保留未知，不生成虚假的准确时长。跨进程用阶段关系和 UTC 展示顺序；单调时钟只计算各自进程内耗时。

旧版退出前刷新纳入已有退出协调预算。主工作区未提交的后台缓存退出最多等待 3 秒，而实施工作树可能未移植该改动；实施时以工作树当前代码为准，设计兼容合并后的共享截止时间，不叠加多个 3 秒等待。记录器需能区分“执行完 flush 回调”和“确认写入成功”，不能只凭回调宣布日志已持久化。

## 文件与并发写入

优先在固定 `Diagnostics/updates/<UUID>/` 下保存升级专用事件，每个写入进程只追加自己的随机命名 JSONL 文件。原 HUD 与新版继续使用普通会话日志。所有文件仍由统一的安全路径访问层管理，目录 `0700`、文件 `0600`，拒绝链接、非普通文件和非当前用户文件。

升级专用文件与普通文件共同受 M1 的 72 小时、10 MiB 全局预算约束，单次升级事件总量另外限制为 64 KiB。容量规划、写入和清理的多进程竞争必须在短小临界区串行化；使用有界或非阻塞进程锁，锁忙时允许跳过诊断并在能够记录时补充缺口，不阻塞安装与主线程。活动文件不得被另一个写入者轮转成无约束的新文件；无法安全腾出空间时跳过新增诊断。

多进程写入器只能追加诊断事件，不能触发普通记录器的 session marker、全局启用、清除或业务初始化。不能假定当前 M1 为单写入者设计的 `DiagnosticStore` 可以直接由多个进程共享使用。

跨进程启用开关与清除代次使用持久控制状态。助手每次准备写入时在同一临界区核验启用状态和代次，不能只相信升级开始时的开关副本。“关闭记录”停止所有生产者后续诊断写入；“清除记录”更换代次并清除自有诊断数据，使旧助手不能重新创建已清除的历史。必要的最小控制状态可保留，但不得包含业务或历史日志。

清除、导出和退出同时发生时，导出快照遵循原 M1 的失效规则。诊断清除不删除 `previous.app`、安装恢复状态、`install.log` 或其他原有恢复材料；这些材料不是新诊断白名单文件，也不会原样导出。

## 恢复与跨版本兼容

正常升级通过现有启动参数定位合法交接；自动启动竞争或人工打开导致参数缺失时，从自有诊断区读取有限的未完成交接条目。只有来源、目标版本、当前安装位置验证和唯一性足够时才关联；存在歧义时保留候选观察与未知状态，不选择时间最近的条目强行关联。

同时存在多个启动尝试时，保持现有单实例保护，不让进度助手争夺 HUD 单实例锁。最终存活的 HUD 继续正常功能；重复启动和缺少回执可以记录，但不为诊断另行启动或终止任何应用。

协议首版明确版本号，新字段尽量可选。支持旧诊断协议时进行类型化解码和安全重建；未知事件或未知协议保留缺口计数，不将未知 JSON 原样导出，也不以迁移方式改写旧记录。升级、回退和新旧程序分别执行时均须满足其能识别的字段边界。

首次从尚无诊断能力的旧版升级，只能保留原来存在的安装状态并从新版开始记录。更重要的是，当前安装脚本和 progress helper 由来源版本准备，不能假定安装包中的新代码能够补录旧助手经历的过程。兼容性验收至少区分：无诊断旧版到新版、支持协议旧版到支持协议新版、升级失败回退到支持协议旧版、回退到不支持协议旧版。

## 业务恢复证据

Codex 持续运行时，升级前后均记录宿主是否运行、实际采用的数据目录来源类别、任务显示和 Hooks 的运行中开关、监测启动或停止原因及扫描批次。不要从已保存偏好直接推断运行中值。

新版分别记录首次业务连接结果、首次任务索引读取结果、首个有效任务开始事件、状态聚合以及主线程接收与显示提交。恢复后没有新任务时，只能说“监测已启动或读取成功”，不能说已验证任务识别正常。Touch Bar 仍只声明显示请求已发出。

不导出宿主 PID、目录或任务 ID 原文；如需核实宿主是否重启，可在本地校验已知宿主进程的 PID 加启动时间并只输出 `sameProcess`、`changedProcess`、`unknown`，把最小交接值限制在私有控制状态内，并按同样期限清理。来源不足时保持未知；不能用宿主版本相同证明宿主没有重启。

## 导出与故障取件

继续使用原 M1 预览快照和 ZIP 流程，将通过白名单校验的跨进程事件合并到 `events.jsonl`，去重键为升级 ID、生产者会话和事件 ID。摘要增加来源版本、目标版本、已观察运行版本、安装结果、各模块恢复状态及采集空窗。

升级事件以同一次导出的截止时间冻结。助手在预览后继续写入，不能改变已经预览的包。若用户选择的时间范围只覆盖升级一半，应明确显示时间范围截断；需要完整升级历史时引导重新选择范围，不能悄悄加入预览范围以外的事件。`manifest.json` 增加生产者覆盖、协议兼容情况、可确认的缺口与截断，不把每个文件末尾不完整一行当成整个文件无效。

新版无法启动时，用户可以通过 Finder 取得固定诊断目录里的已有记录，安装助手事件不依赖新版成功启动才能保存。另保留原安装恢复目录作为独立排查材料；不将其整目录复制进诊断 ZIP。未得到安全记录的步骤明确缺失，不能承诺诊断覆盖所有断电时点。

## 必须验收的场景

| 场景 | 验收点 |
| --- | --- |
| Codex 保持运行，HUD 正常升级 | 旧版、安装器和新版事件可关联；版本准确；业务恢复单列；不要求重启 Codex |
| 升级前有任务，升级后又新建任务 | 保留生产生命周期规则，旧任务未知不伪造 running；新开始事件能沿扫描到显示定位 |
| 新版已启动但连接或任务读取失败 | 安装回执仍按原语义处理，诊断明确业务未恢复，不能只给“升级成功所以正常” |
| 旧 HUD 退出超时，替换失败，回退成功或失败 | 实际阶段和结果正确，已有日志可获取，原安装回退路径不被诊断改变 |
| 新版无法启动、启动回执超时或迟到 | 助手记录独立留存，迟到回执不伪造过去观察，不引起重复替换 |
| 手动打开或自动启动竞争，没有交接参数 | 单实例行为保持，可信唯一关联或明确未知，无凭据或路径泄露 |
| 磁盘满、目录拒绝、半行、助手被终止、锁占用 | 有界失败、不拖住安装，完整旧行可读，缺口不伪造确定数量 |
| 记录关闭、更新期间关闭或清除、新版读取开关 | 所有生产者停止旧代次写入，数据不复活，原恢复材料保留 |
| 多生产者并发、清理与导出重叠 | 无行混写、无越权路径、无容量失控，预览与保存一致 |
| 新旧协议、首次升级、回退不支持诊断的旧版 | 明确能力缺失，不回填不存在的历史，不因未知字段崩溃 |
| 时钟调整、跨午夜、升级事件超出导出范围 | 会话序号和阶段关系有效，跨进程时间不作虚假精确计算，截断明确 |

自动化测试不得操作 `/Applications/GPT TouchBar HUD.app` 或真实 Codex。真实升级、回退及持续运行 Codex 的试用需要操作者按既有授权边界执行；未做则列明缺口。已有 Intel 工具链、实体机和性能缺口继续保留，不以此次隔离测试代替。
