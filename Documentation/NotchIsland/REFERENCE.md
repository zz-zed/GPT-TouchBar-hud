# 二、当前实现为什么不能仅靠微调达到参考效果

两个项目的差异主要在结构，而不只是样式。

| 维度 | 你当前的实现 | CodexIsland 的实现 | 本次应如何改 |
|---|---|---|---|
| 垂直锚点 | 接在摄像头下方 | 整个表面贴屏幕顶边 | 改为顶边一体式结构 |
| 静止形态 | 根据文字测量的摘要条 | 刘海两侧固定宽度的小翼 | 摘要移到悬停态 |
| 状态 | 展开 / 收起 | Compact / Peek / Expanded | 引入明确的三态 |
| 悬停 | 没有独立预览形态 | 只横向露出额度预览 | 新增 Peek |
| 尺寸变化 | 动画中调整整个窗口 | 窗口固定，内部轮廓变化 | 停止逐帧缩放系统窗口 |
| 动画 | 180 ms ease-out，随后显示详情 | 非对称弹簧与分阶段内容过渡 | 使用参考参数与时序 |
| 详情结构 | 一个详情滚动区 | 固定头尾，中间分页 | 分离外壳与业务内容 |

这些差异可在你当前的 `NotchHUDController.swift`、`HUDPresentation.swift`，以及参考项目的窗口控制器和状态模型中直接对应。

还有一个需要一起解决的耦合：你当前的 `update()` 会触发 `relayout()`，而 `relayout()` 会先停止现有过渡。**从代码路径看，数据刷新可能中断正在进行的展开动画。**新实现必须把“数字更新”和“形态切换”分开，而不是每次刷新都重新布局、停止动画。

# 三、最终应该呈现什么效果

## 3.1 Compact：静止时，与刘海融成一体

静止态不再显示整行额度，只保留刘海左右的小翼。

建议业务映射：

```text
                 [应用标记] [ 摄像头避让区 ] [任务状态]
```

左侧使用你应用的简化单色标记；右侧显示执行中、近期完成、未知等状态符号。

这里保留的是你的业务信息，而不是照搬参考项目的两个供应商品牌。关闭任务展示后，右侧改成中性额度标记，不能因为关闭监测就显示“0 个任务”。

**静止态应当满足：顶边贴合、外形稳定、没有额外挂在刘海下面的摘要条。**

## 3.2 Peek：悬停只横向展开，不向下掉出详情

鼠标进入后，外壳向两侧延伸，新增额度胶囊：

```text
[5h 剩余 · 重置] [应用标记] [ 摄像头避让区 ] [状态] [周剩余 · 重置]
```

最关键的视觉细节是：

**两侧原有标记不跟着外壳向外移动，而是保持原来的物理位置；额度内容出现在新增的外侧空间。**

参考项目专门通过固定槽位和标记边距变化实现这一点，这不是普通 `HStack` 增加两个文本就能自然得到的效果。

Peek 的高度不随文字变化，百分比从 `9%` 变成 `100%` 也不应导致外壳宽度抖动。

## 3.3 Expanded：点击后，从同一个外壳向下展开

点击 Compact 或 Peek，进入详情：

```text
┌──────────────────────────────────────────────────────┐ ← 屏幕顶边
│ 左侧标题            摄像头避让            右侧操作     │
│                                                      │
│                    中部业务内容                      │
│                                                      │
│ 页签 / 页码                         更新状态 / 设置    │
╰──────────────────────────────────────────────────────╯
```

这里不是“关闭一个小窗口，再弹出一个大窗口”，而是同一个表面变化。

参考项目的展开层由固定头部、中部内容和固定底部组成。因此翻页时应当**只移动中间的业务内容，标题、设置、同步状态等外围元素保持稳定**。

鼠标移出整个交互表面后回到静止态。开启“始终显示额度”后，静止态改为 Peek，而不是始终展开详情。

# 四、布局尺寸和外形：直接采用参考参数

设：

- `N`：检测得到的摄像头避让区宽度。
- `H`：当前环境下紧凑轮廓的视觉高度。

建议首轮对齐使用以下规格：

| 项目 | 规格 |
|---|---:|
| 每侧标记槽位 | 38 pt |
| 每侧 Peek 额度槽位 | 96 pt |
| Compact 宽度 | `N + 76 pt` |
| Peek 宽度 | `N + 268 pt` |
| Compact / Peek 高度 | 都为 `H` |
| Expanded 标准宽度 | 800 pt |
| 承载窗口基线 | 900 × 360 pt |
| 顶部两个圆角 | 0 |
| 底部两个圆角 | 14 pt，连续曲线 |
| 小翼标记尺寸 | 20 pt |
| Compact 标记距外沿 | 9 pt |
| Peek 标记距外沿 | 105 pt，即 `96 + 9` |

这些是参考源码中的实际值，不是估算值。

## 4.1 外形不能画成四角圆角胶囊

参考外形的准确特征是：

**顶部平直、顶部两角为零、底部为连续圆角。**

因此不建议继续沿用当前的“窄肩连接下方宽面板”路径，也不能直接用一个四角都圆的 `RoundedRectangle` 替代。

## 4.2 窗口贴屏幕顶边，而不是贴刘海底边

新承载窗口位置应按以下关系计算：

```text
windowX = notchCenterX - windowWidth / 2
windowY = screenFrame.maxY - windowHeight
```

动画中改变内部形状，不逐帧改变 `NSPanel.frame`。

900 × 360 pt 是对照基线，不是不可突破的硬限制：如果你的真实详情内容加光晕超出承载范围，需要在打开前完成测量并预留空间。超长内容优先内部滚动，不能无限撑高窗口。

**即使承载窗口因环境变化需要调整，也不应在一次展开动画中反复改变系统窗口边界。**

## 4.3 物理摄像头区域和软件轮廓高度分开保存

建议新布局模型至少保存：

```text
screenFrame
hardwareExclusionRect
notchCenterX
notchWidth
physicalTopInset
visualBarHeight
backingScaleFactor
```

这样才能处理自动隐藏菜单栏、显示缩放和多屏坐标，而不是始终把 `safeAreaInsets.top` 当成所有高度的答案。

参考项目也区分了视觉菜单栏高度和物理安全区，并包含一个减去 1 pt 的经验校准。**这个 1 pt 不能直接当成所有 macOS 环境通用的系统规定。**应提取成可测试的高度策略，用真机数据验证。

# 五、动画：需要复刻参数，也需要复刻先后顺序

只复制弹簧参数，仍然可能做出“像弹窗”而不是“像刘海自然延伸”的效果。外壳、胶囊和正文必须分别组织动画。

## 5.1 核心参数

| 动作 | 对齐参数 |
|---|---|
| 展开外壳 | `spring(response: 0.42, dampingFraction: 0.82)` |
| 收起外壳 | `spring(response: 0.30, dampingFraction: 0.88)` |
| 正文进入 | 贝塞尔 `(0.23, 1, 0.32, 1)`，280 ms |
| 额度胶囊进入 | 延迟 60 ms，再 ease-out 180 ms |
| 胶囊进入位移 | 左右分别从 ±6 pt 到 0 |
| 胶囊退出 | 80 ms |
| 正文退出 | 100 ms |
| 按钮按压 | 缩放至 0.94，110 ms |
| 控件悬停反馈 | 120 ms |
| 横向分页 | 贝塞尔 `(0.25, 0.82, 0.25, 1)`，360 ms |
| 图表样式切换 | 220 ms，透明度 + 3 pt 模糊 + 0.96 缩放 |

来源为参考项目的 `Animations.swift` 和 `IslandRootView.swift`。注意，弹簧的 `response` 是响应参数，**不等于必须在 420 ms 或 300 ms 时强行结束动画**。

## 5.2 悬停进入的时间线

```text
0 ms      外壳开始向左右扩展
60 ms     额度胶囊开始淡入，并完成小幅横向位移
约240 ms  胶囊淡入完成，外壳继续自然收敛
```

原来的两个标记保持物理位置不动。

不建议额外增加一段很长的悬停等待，否则即使弹簧相同，整体反应也会明显慢于参考。

## 5.3 点击展开的时间线

```text
0 ms      外壳立即开始向两侧、下方展开
220 ms    正文开始淡入，垂直位置从 -8 pt 到 0
250 ms    原 Peek 胶囊开始淡出
随后      正文完成进入，外壳自然收敛
```

这些阶段对应参考代码中的实际延迟。

正文按最终详情宽度排版，由外层轮廓裁切；不要在整个面板上使用 `scaleEffect` 来伪装大小变化，否则文字会一起变大，看起来更像放大卡片。

## 5.4 收起时必须避免“整块黑色闪一下”

退出流程建议明确为：

```text
0 ms      正文开始100 ms淡出
20 ms     外壳开始收起
结束      回到Compact，或设置指定的Peek
```

**正文退出和外壳收起要重叠。**

参考代码已经针对等待正文完全消失后才收壳所造成的黑色闪烁，改为 20 ms 后开始收起。

你的实现还应进一步明确：目标状态变为 Compact 时，正在退出的 Expanded 内容层不能立刻从视图树删除；应等它淡出结束再卸载。

## 5.5 动画必须支持快速反向

必须用集中、可取消的过渡管理器，处理这些情况：

| 场景 | 必须发生的行为 |
|---|---|
| 胶囊尚未淡入，鼠标已经移出 | 取消旧的进入任务 |
| 点击后未满 220 ms 就移出 | 不再迟到显示正文 |
| 收起中重新移入 | 从当前尺寸反向展开，不先跳回初始尺寸 |
| 动画中刷新额度 | 更新数字，不停止形态动画 |
| 动画中拔掉显示器 | 取消旧任务，不在旧坐标重新显示 |
| 状态经历 A→B→A→B | 第一轮的延迟回调不能影响第二轮 |

建议每轮过渡带一个 `generation`，所有延迟任务绑定它。**只检查“当前是不是 Expanded”不够，因为状态可能离开后又回到同名状态。**

# 六、交互实现：这里要比参考代码更稳

## 6.1 状态机规则

建议用显式状态代替当前的单个 `isExpanded`：

```swift
enum NotchPresentationState: Equatable {
    case compact
    case peek
    case expanded
}
```

这只是接口规格，不是已提交的实现代码。

主要规则如下：

| 事件 | 行为 |
|---|---|
| 鼠标进入 Compact | 进入 Peek |
| 点击 Compact / Peek | 进入 Expanded |
| 从小翼移动到展开内容 | 保持 Expanded |
| 点击详情空白 | 不自动折叠 |
| 点击刷新、设置、分页按钮 | 只触发按钮动作 |
| 移出整个交互区域 | 回到静止态 |
| 点击外部应用 | 收起，且不吞掉外部点击 |
| 数据更新 | 不改变展开状态 |
| 操作自己的菜单或弹出层 | 暂停 hover 自动收起 |
| 隐藏、锁屏、换屏 | 取消所有旧过渡 |

参考代码中，普通点击只从 Compact/Peek 进入 Expanded，并不是对整个面板做无条件 toggle。这个细节应保留，否则内部按钮很容易出现“点刷新同时收起”的问题。

## 6.2 点击区域不能直接使用目标尺寸矩形

这一点，你当前的实现有值得保留的优势：

你的代码已经用真实 `surfacePath()` 做绘制和命中；参考项目的 AppKit 层主要根据 `model.size` 对应的矩形切换鼠标事件。

新方案应该进一步做到：

> **动画当前画到哪里，点击区域就到哪里。**

不能用“最终 Expanded 的 800 pt 矩形”，去接收一个仍然只有 Peek 大小的界面的点击。

建议区分三个区域：

| 区域 | 用途 |
|---|---|
| 当前绘制路径 | 绘制黑色外壳 |
| 当前点击路径 | 决定哪些真实可见位置接收点击 |
| Hover 保持区域 | 避免穿越摄像头区域或边缘时反复开合 |

透明圆角、光晕、阴影不属于点击区域。Hover 的少量容错也不能变成额外挡住外部应用的点击区域。

## 6.3 视觉与命中共用同一份动画几何

建议由一个 SwiftUI `Animatable` 容器插值宽高，并用插值结果同时生成：

```text
当前尺寸
当前轮廓路径
内容裁切区域
鼠标路由快照
```

通过轻量桥接把这份快照交给 AppKit。不要另外开一个 Timer 计算另一套“看起来相同”的弹簧，两套时序迟早会不同步。

还要在**鼠标静止、但界面正在收缩**时更新命中；不能等到下一次鼠标移动才恢复透明区域的穿透。

## 6.4 保留不抢焦点，不照搬参考的激活行为

参考控制器会在鼠标进入时执行 `NSApp.activate` 和 `window.makeKey()`。你的项目当前使用非激活 `NSPanel`。

本方案建议：

**悬停、展开、刷新都不抢焦点；只有明确打开设置等需要输入的操作才激活对应窗口。**

Apple 对 `.nonactivatingPanel` 的定义也明确是不激活所属应用。:chatgpt-content-reference{index="26"}

与此同时，不应为了复制参考快捷键，偷偷增加全局方向键、Esc 或 Command+数字拦截。参考快捷键依赖其窗口成为 key window；你不能一边保持非抢焦点，一边接管用户正在编辑器中使用的键盘。

首版通过菜单提供对应操作，必要时再增加用户主动进入的“键盘操作面板”模式。

# 七、视觉细节：哪些必须一并复制

## 7.1 颜色、材质和边界

建议默认刘海视觉采用参考基线：

| 元素 | 参数 |
|---|---|
| 外壳 | 不透明黑色 |
| 环境光晕 | `#0047AB` |
| Codex 额度强调色 | `#5AA8F0` |
| 展开描边 | 白色 12%，0.5 pt |
| 彩色光晕 | opacity 0.35，radius 14 pt |
| 展开阴影 | 黑色 0.5，radius 20 pt，向下 10 pt |
| 材质晕染 | 外扩 9 pt，blur 8 pt，opacity 0.55 |
| 扫光线条 | 4 pt，blur 3 pt |

参考的扫光以局部时间视图更新，转速为每秒 100°，即每圈 3.6 秒。

光晕必须位于装饰层，**不参与布局测量和点击命中**。否则会出现外壳尺寸被撑大、图标错位、透明区域挡鼠标的问题。

## 7.2 字体不能全部沿用当前的小号标签

参考项目使用明确的字号层级，例如：

| 用途 | 参考规格 |
|---|---|
| 主要大数字 | 38 pt，semibold，monospaced |
| 图表数值 | 18 pt，semibold，monospaced |
| 标题 | 13 pt，semibold |
| 页签 | 12 pt，medium |
| 普通标签 | 11 pt，medium |
| 按钮 | 11 pt，semibold |
| 时间和次级说明 | 10 pt |

数字字体使用系统 monospaced 设计，而不是仅给普通字体加等宽数字。

但你自己的“监测不完整”“连接异常”等重要说明不能为了追求参考的弱化装饰效果而变得难读。**视觉层级可以复刻，重要信息的可读性不能牺牲。**

## 7.3 减少动态效果和低功耗

正常模式先对齐参考的环境扫光；系统低功耗或应用节能模式下，仅在悬停、刷新、有效告警等状态启用动态装饰。参考源码也对低功耗和窗口遮挡做了区分。

实施要求是：窗口不可见时停止动态装饰；Reduce Motion 时取消弹簧过冲、位移、缩放和持续扫光；Reduce Transparency 时关闭材质晕染。

不能把整个刘海根视图放进高频 `TimelineView`，让全部文字、布局和事件闭包持续重建。

# 八、业务内容如何接入，而不引入新问题

建议最终详情层提供三页：

| 页面 | 内容 | 数据来源 |
|---|---|---|
| 额度 | 5 小时、周额度、重置卡、重置时间、更新时间 | 现有额度状态 |
| 活动 | 执行中、近期完成、未知状态、监测覆盖 | 现有任务状态与反馈 |
| 用量 | 昨日/累计 token、点数余额 | 现有 token 与余额状态 |

这三个页面是**本方案的业务映射**，不是参考项目原有页面名称。

你当前已经有 `HUDMetric.rows(for:)` 和 `NotchTaskPresentation`，其中包含 5h 缺失时使用重置卡、监测未就绪、覆盖不足等规则。新视图应当复用这些语义，而不是根据“能不能拿到一个数字”自行判断状态。

尤其要守住四件事：

**缺失不是 0；剩余额度不是已使用额度；监测关闭不是没有任务；重新渲染不是新的任务完成事件。**

不要为了填满参考样式而新增虚构费用、年度曲线或完整任务列表。页面中没有对应数据就明确表示缺失。

# 十、系统兼容：这几项不能被“复刻效果”带偏

## 10.1 保留整体 macOS 11 支持

你当前 package 的最低系统是 macOS 11，刘海检测已有可用性保护。

不应因为复制参考 SwiftUI 组件就静默提高整个应用的最低版本。新 API 逐项做可用性审计；旧系统上的非刘海功能继续工作，必要的形状用兼容实现。

## 10.2 不把辅助区当成菜单栏空闲区

Apple 的左右辅助区域表示不被摄像头遮挡的屏幕区域，并不表示没有其他应用菜单项。:chatgpt-content-reference{index="36"}

因此，**不能承诺只要用了辅助区域 API 就绝不遮挡菜单栏**。

实际策略应该是：Compact 尽量窄；Peek 暂态出现；打开自己的菜单时收起；长菜单、自动隐藏菜单栏和缩放配置做真机验证。透明区域穿透只能解决事件阻挡，不能解决黑色外壳在视觉上覆盖了菜单文字的问题。

## 10.3 不随意提高窗口层级

首版保留你当前非激活 Panel 和窗口策略，不为了“永远可见”直接换成极高层级。

尤其不能把现有的全屏排除行为误判为忘记写 `fullScreenAuxiliary`。你的代码明确采用了相应排除策略，Apple 文档也说明 `fullScreenPrimary` 可用于退出加入其他应用全屏 Space 的行为。:chatgpt-content-reference{index="38"}

动画对齐和全屏产品策略应分开决策。

## 10.4 保留用户显示意图

用户原本选择桌面浮窗，就不自动改成刘海；用户原本隐藏，唤醒后也不能自行显示。新设置只增加“始终显示额度”等能力，不重置已有 `hud.displayMode`、`hud.requestedVisible` 和 `menu.displayMode`。这些偏好目前已经存在。

# 十一、按六个阶段落地

| 阶段 | 要做什么 | 完成条件 |
|---|---|---|
| **0：冻结参考** | 固定提交、固定数据，录制参考三态与交互 | 有同机对照基准，而不是凭印象调动画 |
| **1：窗口与几何** | 顶边锚点、固定承载、连续轮廓、真实命中 | 静态三态正确，透明区域穿透且不抢焦点 |
| **2：状态与输入** | 悬停、点击、移出、菜单保持、手势捕获 | 状态机与输入测试通过 |
| **3：动画对齐** | 弹簧、分阶段内容、反向、取消、减少动态效果 | 无黑闪、无跳变、无迟到回调 |
| **4：真实内容** | 额度/活动/用量页、错误与未知、中英文、偏好迁移 | 与现有表面数据一致 |
| **5：兼容与发布** | 多屏、全屏、睡眠、性能、打包、授权声明 | 真机报告和可回滚预发布产物 |

**不要先花大量时间把详情页画漂亮，再来处理透明窗口挡点击。**
第一阶段就应验证穿透与焦点，因为这决定承载方案是否成立。

过渡期保留内部 legacy/island 渲染开关，但两个刘海窗口绝不能同时显示。回滚只切换呈现层，不重置额度服务、任务监测和用户偏好。

# 十二、怎么判断真的做到了，而不是“看着差不多”

完整文档列出了 51 项用例。最关键的发布门槛是：

| 验收方向 | 必须证明 |
|---|---|
| **轮廓** | 顶边贴合、底部曲线正确，没有另挂摘要条 |
| **空间关系** | Peek 外扩时图标不漂移，数字变化不改变外壳宽度 |
| **动画** | 进入有层次，退出不黑闪，反向操作不跳回初始状态 |
| **鼠标** | 透明角、光晕和未展开区域不会挡住其他应用 |
| **焦点** | 编辑器中持续输入时，悬停和刷新不会抢键盘 |
| **数据** | 未知不变成 0，完成提示不重复播放，各表面额度一致 |
| **系统** | 拔屏、锁屏、唤醒、Space 切换后仍保持用户意图 |
| **发布** | 新文件和资源真实进入安装包，最低系统与架构没有回退 |

本地没有带刘海设备时，可以做一个注入式实验台：输入屏幕坐标、刘海宽高、缩放倍率，显示实际点击路径、Hover 区和动画时间。它能验证多数布局与状态问题，但**不能替代真实硬件的接缝、菜单遮挡和窗口层级验证**。

真机对照应该在同一台设备、相同缩放和菜单栏设置下分别运行两者。软件动画用录屏比较；实体摄像头与黑色外壳的接缝再用外部相机确认。

---

**最终建议就是：保留你现有应用的“数据与系统能力”，把刘海部分换成 CodexIsland 的“固定顶边外壳 + 三态交互 + 分层弹簧动画”。**

其中最不能省略的不是某个光晕参数，而是：**固定承载窗口、当前呈现几何与命中一致、可取消的动画状态机，以及不抢焦点和原有数据语义的回归验证。**这些都成立后，才能真正得到参考仓库那种“内容从刘海自然延伸出来”的效果。
