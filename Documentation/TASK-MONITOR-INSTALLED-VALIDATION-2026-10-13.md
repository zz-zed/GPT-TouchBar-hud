CPU 以进程所有线程累计 CPU 时间差除以单调墙钟时间计算，100% 表示一个 CPU 核。测量包含原生界面、额度服务、任务监测及开启的本地诊断；没有关闭功能来降低占用。前后是同机先后测量，运行期间日志仍在增长，最终窗口包含真实任务测试；它与第一阶段冻结输入基准的条件不同。

首次替换后，LaunchServices 仍启动了移至备份目录的原二进制。磁盘哈希不足以证明当前运行代码；通过采样的 Mach-O UUID 和 `lsof` 的 `txt` 映射发现了这一点。该次 28.88% 的测量属于旧版，未计入新包结果。重新注册安装包后核对了真实加载路径，并再次验证普通 `open -a` 会加载正确包。

普通重启后，缓存在 0.26 秒时匹配原集合，但可能读到上次进程留下的数据，因此不把它作为恢复时效证据。3.45 秒取自新进程诊断会话中的 launch 与实际菜单栏渲染请求。两次新任务开始时效存在差异；第一次未单独测量索引提交和日志落盘时间，原因尚不能确定，不承诺全部新任务在两秒内显示。

## 任务恢复修复

旧实现把 HUD 的观察代次变化当作失去运行资格：重启、模式切换和唤醒会把原 active 降为 unknown，即使读到当前工具活动也不能恢复。现场因此漏掉两个仍在执行的任务。

- 显式开始事件保存轮次、原始时间、位置和文件代次。恢复必须通过日志身份和断点校验，补读至完整记录边界，具有未过期且属于同一轮次的证据，无坏记录缺口、容量缺口或终态否决。
- 老缓存没有新开始依据时，只对未结束候选重读日志，不能直接信任 `lastKnownPhase=active`。已验证的新缓存继续复用偏移，不重读无关的大文件。
- 恢复计数记录为 `journalRecovered`，不要求用户重新发送消息。只有工具事件且找不到开始的任务继续待核对；无 turn ID 的 Token 统计不改变状态和时效。
- 已结束轮次进入有界关闭集合。迟到活动和相同 turn 的重复 start 不能复活它；同一聊天不同 turn 的真实开始正常计数。关闭依据在断点恢复和文件重建时保留，容量不足时降为待核对。
- 匹配终态在补读中优先处理；历史完成不重放提示。半行不能授权恢复，但已经完整解码的终态能及时关闭轮次。
- 已知宿主断开保存恢复时间下限；恢复期间的旧工作不能绕过断开边界。回调代次取消门禁和公平读取继续生效。

以上仍是本机日志推断，不是宿主直接提供的执行真值；沿用 30 分钟证据时效。长时间静默、永久缺失终态、无法识别的宿主内部重启仍是日志来源的边界。本次未完整实现此前恢复设计中的系统睡眠时长补偿或更强的来源进程身份适配。
