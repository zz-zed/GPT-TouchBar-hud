# 任务漏计诊断追加实施方案

2026-10-08。用户已授权设计并交原实施会话执行，属于 [诊断 M1](DIAGNOSTICS-IMPLEMENTATION-PLAN-2026-10-08.md) 默认基础记录。实施会话为“内置诊断 M1 迭代实施”，工作树 `/Users/didi/.codex/worktrees/f5be/TouchBarCodexToken`；本文件为实施与验收要求，不表示功能已经完成。

## 要解决的诊断缺口

[排查 TouchBar HUD 任务状态显示](codex://threads/01a11aa3-83f2-7201-92a4-0b301afc29dc) 已用现有生产读取器隔离复现：明确开始后计数为 1，日志大增量触发跳读与状态清空，计数变为 0，继续执行仍无法恢复。现场约 489 KB 单条工具结果与该路径相符；其他侧边栏任务尚未全部逐项核齐，不能把所有差额都归到同一原因。

当前诊断实现有扫描批次、读取截断次数、聚合结果、主线程接收和显示提交，能够定位到模块，但没有逐任务别名、读取位置、状态转换原因和完整展示快照。目标是让一次导出的包能够回答：数字从 3 变成 1 时，具体哪两个匿名任务退出计数，各因什么生产决定，界面消费了哪份结果。

本次只增加可观察证据和验证，不修复或重定义生产计数。连续读取、分页任务库存、断点恢复及统一状态引擎按 [任务状态可靠性改造方案](TASK-STATUS-RELIABILITY-PLAN-2026-10-08.md) 单独实施。新增诊断接口应可由后续引擎复用，不再建立一个独立任务推算器。

## 完成后的证据链

同一条链路贯穿生产发现、生产读取、生命周期判断、计数成员变化、协调层投递及 Touch Bar、菜单栏、浮窗、刘海的状态消费。公共关联字段包括记录进程会话、监测代次、扫描批次和展示快照编号。所有编号都是本地诊断代号，不能用原始 thread、turn、文件路径或账号标识替代。

| 事件类别 | 必须提供的字段或证据 | 可回答的问题 |
| --- | --- | --- |
| 任务身份 | `taskAlias`、必要时 `turnAlias`、文件代次、身份来源与关联可信状态 | 同一任务是否重复计数，是否换了轮次或文件 |
| 读取边界 | 文件长度、读取前后位置、已读取字节、已跳过字节、积压、解析待完成字节、固定读取分支 | 是否超过预算、发生跳读、截断、轮转或半行丢弃 |
| 生命周期 | 前后生产状态、转换原因、证据事件种类、是否接受、未接受原因 | 为什么从执行变为未知或结束，为什么后续活动未恢复 |
| 计数成员 | 每个任务的 `countedBefore` / `countedAfter`，移除或加入原因 | 总数变化由哪些任务组成，是否总数不变但成员发生变化 |
| 发现覆盖 | 来源范围、查询上限、实际返回量、有效量、路径拒绝量、遍历完成状态、库存加入与移除原因 | 任务未入选、被替换出库存，还是入选后失去状态 |
| 展示快照 | 原始运行数与未知数、对应计数成员、完成反馈等呈现变换、快照编号 | 主线程和四个显示端是否消费同一份状态 |

每个字段都有明确计量单位和未知值。没有执行查询不写为零；`budgetReached` 不等于确认发生遗漏；读取失败不是无任务；诊断截断与生产日志跳读分别命名，避免混淆。

## 匿名身份与隐私

优先基于生产已经持有的稳定任务身份在内存中分配会话内随机代号。现有普通模式只以 rollout 路径作为键时，可先建立匿名文件身份，但必须注明 `identityKind=file`，不能宣称已证明是一对一的主聊天身份。如需补充索引 thread ID，只读必要元数据且不改变生产筛选、排序或去重；原值仅用于内存映射。

同一代号在进程内稳定，清除诊断后重新建立代号域；HUD 重启后使用新域。跨升级仅通过现有升级 ID 关联进程级证据，不持久化原始任务映射来强求逐任务跨进程相等。无法关联时明确显示未知；后续若需要跨重启同一任务对照，应单独设计受保护映射。

映射必须有内存上限，初始建议最多 4096 项，优先保留当前库存项；退役身份超限时淘汰，后续重见使用新代号并记录关联断点，绝不把旧代号分配给另一个身份。分配、查找和编码不得在主线程执行文件查询。

禁止写入任务标题、提示词、工具名称或参数正文、响应正文、账号、真实用量、原始 thread/turn ID、完整路径和 inode 原值。文件仅通过匿名代号与代次表示；版本、架构、数值偏移等元数据继续做类型和大小校验。字段通过明确结构或枚举扩展，不开放任意字符串 payload。

## 生产采集点

### 读取器与状态转换

普通模式在 `TaskLogCursor.read` 的决策点捕获读取前状态、位置及文件长度，在文件重置、超预算跳尾、丢弃首行、超大待完成行及正常读取完成处分配固定原因。记录发生在决定实际产生的地方，不能仅用批末的 `truncatedCount` 推断是哪个任务触发。

生命周期策略调用前后捕获固定事件类型、旧状态、新状态和接受或拒绝原因。至少区分明确开始、完成、中断、轮次不匹配、缺少开始证据、旧时间戳、历史基线限制和终态后迟到活动；以当前代码真实分支为准，不臆造尚未实现的等待用户状态。

`monitoredSummary` 的静默过期、首次发现基线等派生计数变化也要记录。索引刷新替换字典时先观察被移除成员的计数状态，再记录移除原因，避免对象删除后丢失解释。诊断关闭时跳过这些额外编码与映射工作，不改变读取预算或状态结果。

Hooks 在实际证据读取器和 reducer 边界采集对应事件，仅在 `TaskMonitoringCoordinator` 记录汇总不足以覆盖。保持 HookCore 与应用存储解耦，用类型化观察回调或轻量记录接口输出；缺少某项内部证据时不能照抄普通模式的结论。

### 发现与覆盖

当前生产查询只取最近 32 项。默认记录固定查询策略、上限、实际行数与筛选结果，明确 `coverage=limited` 或 `unknown`，不能因为返回 32 个就断言全部候选只有 32 个。

区分生产已经看到的路径拒绝、源类别过滤、库存替换和查询上限。没有读取的行，不能声称知道被排除任务身份或数量。若采用有界的第 33 项探测，作为单独只读诊断观察，不送入生产计数，标记非原子观察时间，并设取消与耗时预算；不要为补诊断默认每 2 秒全量扫描数据库。不能安全探测时保留覆盖受限即可。

对于已经持有、后被刷新移除的任务，必须记录具体匿名别名、移除前是否计数和“离开当前查询结果”等实际原因。除非有明确分页证据，不把移除原因直接定性为第 33 项挤出。

### 计数与显示

每次计数成员或呈现状态变化都生成新的快照编号，即使总数相同也要能记录成员替换。将相同编号随生产结果传递到主线程及四个显示端；不能仅在 AppDelegate 调用更新后统一写一条 `uiSubmitted` 就声称每个端都接收。

各端在实际消费位置记录输入编号、逻辑任务数、呈现类别（执行、完成反馈、中性、关闭等）、紧凑显示规则如 `9+`，以及未提交或被跳过的固定原因。继续区分“已接收数据”“已请求渲染”和“实体可见未知”；诊断不改变普通模式界面、不新增错误 tooltip。

复用上一份任务快照进行额度或布局刷新时沿用其编号；完成反馈计时器引起呈现变化时另记呈现修订及原因。旧代次回调被丢弃、显示开关关闭、该硬件不适用，都要与正常更新分开。不得为了诊断强制显示隐藏窗口。

## 记录量与导出解释

保留原 M1 的 72 小时、10 MiB、单事件 4 KiB、队列上限及跨进程预算。正常稳定轮询不逐条持久化，只记录新身份、重要读取异常、状态或计数成员变化及显示快照变化；重复拒绝的弱事件可按同任务与同原因有界聚合。开始、终态、计数变化和库存移除不得被不同任务共享的错误聚合吞掉。

每个展示快照应具备可核查的计数成员清单或关联到已保存的成员检查点。清单超过单条上限时分页，记录快照 ID、页序、总页数和成员总量。日志轮转、队列丢弃、时间范围截断或身份淘汰导致页面/前序缺失时，摘要声明证据不完整，不从残存成员推导完整运行数。

延续冻结预览与 ZIP 导出，将新事件加入 `events.jsonl`，摘要给出计数变化、对应匿名任务、原因及显示投递情况。不要读取原会话正文补齐缺口，也不要在导出时重新运行状态推算器。若未来为长时间稳定运行增加低频检查点，必须纳入现有调度和资源预算，不增加高频轮询。

以下仅是预期证据形态示例，不是已采集数据：

```text
批次 B12：T2 counted=true，状态 running
批次 B13：T2 增量超过读取预算，跳读 N 字节，running → unknown
批次 B13：T2 counted=true → false，原因 read_budget_skip
快照 S8：运行数 3 → 2，移除成员 T2，成员证据完整
快照 S8：主线程接收；各端分别记录已消费或跳过原因
批次 B14：T2 收到 execution 类事件，因缺少有效开始证据未重新激活
```

如果可靠性修复已进入实施分支，超预算后的轨迹应变为“继续分批读取、保留生产状态”，不能为复现旧问题恢复有缺陷的控制流。

## 验收用例与判定

测试输入的真实任务集合由独立夹具清单确定，不能由待测解析器再次计算出来。使用真实生产 `read`、调度、状态聚合、主线程和导出路径；仅调用 `consume` 或检查日志中出现 `truncated` 不能通过验收。

| 场景 | 必须从诊断包中回答 |
| --- | --- |
| 3 个任务中 1 个遇到约 489 KB 工具结果 | 哪个任务、精确输入字节数、读取位置变化、是否清空、为什么退出计数，其余任务是否受影响 |
| 增量 601826 字节、256 KiB 边界前后、2 MiB 多行或巨行 | 区分跳读、待完成行清空和普通读取，记录实际字节数；含换行的夹具总长度必须明确 |
| 大增量后持续工具或 Token 活动 | 被哪个规则拒绝恢复，诊断不泄露工具正文或用量 |
| 完成后迟到事件 | 保持不复活，记录拒绝原因；不能通过诊断改写生产结果 |
| 33 与 65 个候选任务 | 可见库存与覆盖限制明确，已持有任务被移除可定位；未观察身份保持未知 |
| 任务 A 结束同时任务 B 开始，总数不变 | 成员替换仍有轨迹，快照和各端结果一致 |
| 同一任务轮次变化、日志轮转或截断 | 匿名任务、轮次及文件代次不混淆，旧证据不串到新任务 |
| 重启、升级、唤醒和模式切换 | 代次与基线变化可解释，结合升级 ID 区分原进程和新进程；跨进程任务映射未知如实呈现 |
| UI 隐藏、任务关闭、紧凑显示及完成反馈 | 各端接收的快照与显示策略可解释，无实体显示成功的虚假声明 |
| 队列满、日志轮转、选定范围缺前序或清单缺页 | 摘要标记不完整，不能把不完整证据作为全量成员清单 |
| 隐私与资源 | 包内及所有输出渠道无原始 ID、路径和正文；映射、文件与队列上限有效，静态空闲轮询不增加记录 |

针对尚未修复的读取器，允许在报告中证明“成功捕获了生产缺陷”，但测试名称及断言必须区分“诊断证据验收通过”和“任务计数正确性失败”。不允许把运行任务归零定义为计数正确，也不声称这些测试已经修复故障。

普通日志和 Hooks 都要覆盖实际读取到导出的链路；不能用手工构造事件代替接入验证。新增测试纳入现有 `test-diagnostic-logging.sh`，同时运行受影响任务、Hooks、连接、显示、升级与导出回归。真实机逐任务对照仍需独立证据，无法连接同一宿主权威状态的限制继续保留。
